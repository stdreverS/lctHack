# 2D-симуляция: модель и допущения

Симуляция — единственный расчёт, который выполняется на фронтенде (CLAUDE.md, раздел 4).
Она не заменяет экономику, а проверяет её: показывает, справляется ли подобранный парк
роботов с пиковым потоком заявок на плане объекта.

Код:

| Файл | Что делает |
|---|---|
| `frontend/src/types/sim.ts` | типы `SimInput`, `Segment`, `SimResult` |
| `frontend/src/sim/random.ts` | детерминированный генератор (mulberry32), поток Пуассона |
| `frontend/src/sim/engine.ts` | `runSimulation(input) → SimResult`, константы `SIM_MODEL` |
| `frontend/src/sim/renderer.ts` | кадр по модельному времени и отрисовка на Canvas 2D |

`runSimulation` — чистая функция: не читает время, DOM и `Math.random()`, ничего не меняет
снаружи. Один и тот же вход, включая `seed`, всегда даёт один и тот же результат — прогон
можно повторить и приложить к расчёту.

## Вход и выход

```ts
runSimulation({
  seed: 42,                 // зерно генератора
  simHours: 1,              // длительность прогона, ч
  layout,                   // ObjectType.layout: зоны и их координаты, м
  demand: { peakOpsPerHour: 350, avgRouteM: 120 },
  robots: { count: 12, speedMps: 1.5, handlingSec: 30, autonomyH: 8, chargeTimeH: 2 },
}) // → { segments, kpi, queueByMinute, robotsUtilization }
```

`segments` — лента отрезков по каждому роботу (`moving_empty`, `moving_loaded`, `handling`,
`charging`, `idle`) с временем в секундах и координатами в метрах: из неё рисуется анимация.
Отрезки одного робота идут подряд и без разрывов, поэтому позицию на любой момент времени
рендерер получает линейной интерполяцией.

`kpi` — тип `SimKpi` из контракта API: он уходит на сервер в поле `CalcRequest.simulation`.

## Как устроена модель

Дискретно-событийная: время двигается не тактами, а от события к событию (поступление
заявки, освобождение робота, приезд на зарядку, конец зарядки), поэтому час работы
пятидесяти роботов считается за десятки миллисекунд.

1. **Поток заявок.** Заявки поступают пуассоновским потоком со средней интенсивностью
   `demand.peakOpsPerHour`. Интервал между заявками — экспоненциальный: случайные всплески
   и провалы нагрузки получаются сами, без отдельного «коэффициента пика».
2. **Маршрут заявки.** Пара зон выбирается по смеси маршрутов: приёмка → хранение (35 %),
   хранение → отбор (40 %), отбор → отгрузка (25 %). Точки внутри зон случайные. Если в
   плане нет нужной зоны, правило выпадает; если не осталось ни одного правила — берутся
   любые две рабочие зоны, а при одной зоне маршрут замыкается внутри неё.
3. **Длина маршрута.** Схема даёт только координаты, расстояние берётся из параметров
   объекта: все длины нормируются так, чтобы средний гружёный маршрут прогона равнялся
   `demand.avgRouteM`. План объекта может быть условным — на цифры KPI это не влияет.
4. **Выполнение заявки.** Свободный робот берёт самую старую заявку из очереди (FIFO);
   из свободных роботов едет ближайший к точке загрузки. Цикл: порожний переезд →
   погрузка `handlingSec` → гружёный переезд → разгрузка `handlingSec`. Заявка считается
   выполненной в момент окончания разгрузки. Если задано `robots.opsPerHour` (производительность
   из каталога), весь цикл растягивается или сжимается до `3600 / opsPerHour` с с сохранением
   пропорций: скорость и маршрут определяют только анимацию, а не число заявок в час.
5. **Заряд.** Расходуется по времени работы: полный заряд равен `autonomyH` часов работы.
   Когда остаток опускается ниже порога, робот едет в зону `charging` и заряжается
   `chargeTimeH` часов. Зарядных мест столько, сколько указано в `Zone.slots`; если все
   заняты, робот ждёт очереди (это время идёт в простой). Пока робот едет на зарядку или
   заряжается, он не берёт заявки.

## Константы модели

Все допущения собраны в одном объекте `SIM_MODEL` (`frontend/src/sim/engine.ts`).

| Константа | Значение | Смысл и почему так |
|---|---|---|
| `engineVersion` | `sim-1.2` | версия движка; попадает в `SimKpi.engineVersion` |
| `handlingSec` | 30 с | погрузка или разгрузка, если значение не задано на входе; демо-оценка для паллетных операций |
| `chargeThreshold` | 0,2 | заряд ниже 20 % — робот едет на зарядку; обычная практика эксплуатации AMR |
| `warmupSec` | 600 с | первые 10 минут не учитываются в KPI: в начале прогона все роботы свободны и очередь пуста, иначе производительность завышается |
| `minSpeedMps` | 0,1 м/с | нижняя граница скорости: в каталоге скорость может быть не указана |
| `chargerSlots` | 1 | зарядных мест, если в зоне не задано `slots` |
| `maxTasks` | 200 000 | предел числа заявок за прогон: защита от абсурдного спроса |
| `routeMix` | 35 / 40 / 25 % | доли маршрутов приёмка → хранение → отбор → отгрузка |
| `busyShare` | 0,9 | выше этой загрузки узкое место — нехватка роботов |
| `chargingShare` | 0,2 | выше этой доли времени на зарядке узкое место — зарядка |
| `confirmPercent` | 90 % | порог подтверждения расчёта (см. ниже) |

## KPI

Считаются по окну измерения: от `warmupSec` до конца прогона (если прогон короче разгона,
берётся весь прогон).

| Поле | Как считается |
|---|---|
| `throughputPerHour` | выполненных заявок в окне, приведено к часу |
| `targetPerHour` | `demand.peakOpsPerHour` |
| `achievedPercent` | `throughputPerHour / targetPerHour × 100` |
| `avgUtilization` | средняя доля времени робота на переездах и операциях с грузом |
| `idleShare` | средняя доля простоя, включая ожидание зарядного места |
| `chargingShare` | средняя доля зарядки вместе с дорогой к зарядным местам |
| `maxQueue` | наибольшая длина очереди заявок в окне |
| `bottleneck` | фраза на русском: нехватка роботов, зарядка, операции с грузом или длина маршрута |
| `confirmsCalculation` | `achievedPercent >= 90` |

Порог 90 %, а не 100 % — допущение команды: заявки поступают случайным потоком, и за один час прогона их приходит в среднем столько, сколько задано целью, но с разбросом (30 зёрен на демо-складе при парке с запасом: от 90,7 до 112,5 %, в среднем 101,2 %). Поэтому даже достаточный парк по одному прогону может показать меньше 100 %; порог выбран ниже нижней границы этого разброса. Недостаточный парк порог не проходит: на демо-складе 8 роботов AMR-600 вместо расчётных 15 дают 80,8 % цели — «не подтверждён».

`avgUtilization + idleShare + chargingShare = 1`: время каждого робота разложено полностью.
`queueByMinute` — длина очереди на конец каждой минуты, `robotsUtilization` — загрузка
каждого робота отдельно (для панели KPI и подсветки роботов на плане).

## Экран «Симуляция» (шаг 7 мастера)

| Файл | Что делает |
|---|---|
| `components/wizard/StepSimulation.vue` | сборка входа, статусы, переключатель сценария |
| `components/sim/SimulationCanvas.vue` | холст, модельное время, PNG текущего кадра |
| `components/sim/SimControls.vue` | «Запустить», «Пауза», «Сначала», скорость, перемотка |
| `components/sim/SimKpiPanel.vue` | вердикт, KPI, очередь и загрузка каждого робота |
| `components/charts/QueueChart.vue` | очередь заявок по минутам |
| `utils/simInput.ts` | вход движка из состояния мастера |

Вход собирается по выбранному сценарию (покупка или RaaS):

- число роботов — `metrics.robotCount.value` из расчёта сервера;
- производительность (`perfOpsPerHour`), скорость, автономность и время зарядки — из `Robot.specs`;
- целевая производительность — `metrics.robotCount.inputs.targetPerHour` (то самое значение,
  по которому сервер считал парк), иначе оценка по параметрам объекта;
- средняя длина маршрута — параметр `avgRouteM` (или `bagTransferM`);
- план — `ObjectType.layout`.

Чего нет в каталоге, подставляется из `SIM_FALLBACK` (`utils/simInput.ts`) и выводится на экран
отдельной строкой — пользователь видит, что это допущение, а не данные.

Если у типа объекта `layout = null`, экран говорит «Симуляция пока доступна для склада» и
предлагает перейти к экспорту: переход по шагам не блокируется.

Прогон считается синхронно и занимает десятки миллисекунд (час работы 50 роботов), поэтому
Web Worker не используется; перед расчётом экран отдаёт браузеру кадр, чтобы показался
статус «Идёт расчёт модели…».

Вердикт под холстом: «Расчёт подтверждён: N роботов обеспечивают X % целевой производительности»
либо «Расчёт не подтверждён: …» с кнопкой «Пересчитать с N+1 роботом» — она ставит
`overrides.robotCount` выбранному сценарию и возвращает на шаг «Экономика».

KPI последнего прогона хранятся в store (`simKpi`). В режиме проекта кнопка «Сохранить расчёт»
(шаг 8) отправляет их полем `simulation` в `POST /calculations` — если они получены для текущих
параметров и сценариев; у гостя расчёт не сохраняется.

## Проверка

```
cd frontend && npx vitest run src/sim
```

Тесты (`src/sim/engine.test.ts`, `src/sim/random.test.ts`, `src/sim/renderer.test.ts`,
`src/utils/simInput.test.ts`) закрывают: воспроизводимость по
seed, рост производительности с числом роботов, нулевой парк, рост очереди при большом
спросе, полноту разложения времени, работу зарядки и очереди к зарядным местам,
соответствие среднего маршрута параметру `avgRouteM` и скорость прогона (час работы
50 роботов — быстрее секунды).
Отдельно проверяются кадр по времени и масштаб (`renderer.test.ts`) и сборка входа из
состояния мастера (`simInput.test.ts`).

## Связь с расчётом экономики

Симуляция не пересчитывает экономику, а проверяет её предпосылку — что расчётный парк
справляется с пиковым потоком.

| Что берётся из расчёта | Откуда |
|---|---|
| Число роботов | `metrics.robotCount.value` сценария (с ручной правкой, если она есть) |
| Целевая производительность | `metrics.robotCount.inputs.targetPerHour` — та же пиковая потребность, по которой сервер считал парк |
| Производительность робота | `specs.perfOpsPerHour` из каталога — та же, что в формуле числа роботов |

Сервер закладывает в число роботов загрузку, готовность и резерв (`docs/economics.md`,
формула 2), поэтому парк обычно больше минимально нужного, и симуляция показывает загрузку
заметно ниже 100 % (демо-склад: 15 роботов, загрузка 63 %, 95 % цели).

Что дальше делает результат:

- вердикт «Расчёт подтверждён / не подтверждён» на шаге 7, на шаге 8 и в отчёте;
- кнопка «Пересчитать с N+1 роботом» ставит ручное число роботов и возвращает на шаг
  «Экономика» — экономика пересчитывается сервером;
- KPI сохраняются вместе с расчётом проекта (`CalcRequest.simulation`) и видны в истории;
- печатный отчёт показывает KPI; если симуляцию в сессии не запускали, отчёт прогоняет её сам
  с тем же зерном.

## Допущения и упрощения

| Допущение | Значение | Почему так |
|---|---|---|
| Длительность прогона | 1 час (`SIM_HOURS`) | Проверяется пиковый час — тот, по которому считается парк |
| Разгон | первые 10 минут не учитываются | В начале все роботы свободны, иначе производительность завышается |
| Поток заявок | пуассоновский, средняя интенсивность = цель | Случайные всплески нагрузки без отдельного коэффициента |
| Время заявки | `3600 / perfOpsPerHour` с, если производительность есть в каталоге; иначе — по скорости, маршруту и `handlingSec` | Согласованность с формулой числа роботов |
| Смесь маршрутов | приёмка → хранение 35 %, хранение → отбор 40 %, отбор → отгрузка 25 % | Типовой складской поток; демо-оценка |
| Порог подтверждения | 90 % цели | Разброс случайного потока за один час: 90,7–112,5 % цели при достаточном парке |
| Зерно генератора | фиксированное (`SIM_SEED`) | Одинаковые входные данные — одинаковый результат |
| Подстановки | скорость 1,2 м/с, автономность 8 ч, зарядка 2 ч, цель 100 опер./ч, маршрут — среднее из ширины и длины плана (`SIM_FALLBACK`, `avgRouteM`) | Если данных нет в каталоге или параметрах; выводятся на экран |
| План объекта | условный план склада 120 × 100 м (`ObjectType.layout`) | Длины нормируются по `avgRouteM`, поэтому план влияет только на картинку и доли маршрутов |

## Ограничения

- Все роботы в прогоне одинаковые: симулируется один сценарий и одна модель робота.
- Геометрия упрощена: роботы едут по прямой между точками, проходы, перекрёстки и объезд
  препятствий не моделируются; ширина проходов проверяется отдельно, на шаге подбора.
- Роботы не мешают друг другу: нет заторов в узлах и очередей на местах погрузки.
  Поэтому симуляция даёт скорее оптимистичную оценку пропускной способности.
- Время на доступ к ячейке хранения (подъём, позиционирование) заложено в `handlingSec`.
- Заявки, взятые в работу до конца прогона, доигрываются до конца, но в KPI учитывается
  только время внутри окна измерения; новые заявки после конца прогона не назначаются.
- Если в плане нет зоны `charging` или не задана автономность, заряд не расходуется и
  `chargingShare = 0`: считается, что подзарядка укладывается в перерывы.
- Симуляция ничего не считает про деньги: экономика и окупаемость — только с сервера.
- Если в каталоге есть производительность, время погрузки и переездов масштабируется под неё:
  скорость робота на анимации может не совпадать с паспортной.
- Результат одного прогона зависит от случайного потока: другой seed даёт 90–113 % цели при том
  же парке (30 зёрен на демо-складе); серия прогонов не выполняется.
- План есть только у склада; для аэропорта и больницы симуляция недоступна.
