# Подбор и ранжирование решений

Документ для п. 6.4 ТЗ. Описывает правила, которые работают в демо: модель моков
`frontend/src/mocks/data/recommendation.ts` (вызывается из `POST /calculations`, поле
`recommendation`). Серверное ядро `backend/src/Robo.Core/Recommendation/StubRecommendation.cs`
пока возвращает фиксированный список для демо-склада и правил не содержит.

## 1. Кандидаты

В подбор попадают роботы каталога, у которых:
- в `objectTypes` есть выбранный тип объекта;
- робот-уборщик (`solutionType = cleaner`) — только если среди процессов выбран `cleaning`
  («Уборка»).

Остальные роботы в подборе не показываются вовсе.

## 2. Проверки

Для каждого кандидата выполняются проверки. У каждой — результат `pass` (пройдена), `fail`
(не пройдена) или `unknown` (нет данных), требуемое и фактическое значение и готовая фраза.

| Проверка | Критичная | Когда выполняется | Требуется | Фактически | Результат |
|---|---|---|---|---|---|
| Грузоподъёмность (`payload`) | да | задан `unitWeightKg` (склад) или `loadKg` (аэропорт, больница); не для уборщиков | масса груза | `payloadKg` робота | `pass`, если грузоподъёмность ≥ массы; `unknown`, если у робота нет данных |
| Ширина прохода (`aisle`) | да | задан `aisleWidthM` (склад) или `corridorWidthM` (больница); не для систем хранения `asrs` | `minAisleM` робота | ширина прохода объекта | `pass`, если `minAisleM` ≤ ширины; `unknown`, если у робота нет данных |
| Производительность (`performance`) | да | не для уборщиков | пиковая потребность, опер./ч (`docs/economics.md`, формула 1) | `perfOpsPerHour` робота | `pass`, если нужное число роботов ≤ 40; `fail`, если больше; `unknown`, если нет производительности |
| Автономность (`autonomy`) | нет | всегда | длительность смены | `autonomyH` робота | `pass`, если заряда хватает на смену; `fail` — понадобится подзарядка в смену |
| Достоверность данных (`dataConfirmed`) | нет | всегда | — | признак `confirmed` | `pass` — подтверждено источником; `unknown` — нет |

Число роботов в проверке производительности считается по той же формуле, что и в экономике
(`docs/economics.md`, формула 2). Предел 40 роботов — допущение команды (`maxFleet`).

## 3. Статус

Правило из контракта API:

| Условие | Статус | Группа на экране |
|---|---|---|
| есть критичная проверка `fail` | `excluded` | «Не подходит» |
| иначе есть критичная проверка `unknown` | `needs_check` | «Требует проверки» |
| иначе | `recommended` | «Рекомендовано» |

Некритичные проверки на статус не влияют, но учитываются в балле (фактор «Соответствие объекту»).
Порядок в ответе: `recommended` → `needs_check` → `excluded`, внутри группы — по убыванию балла.

Робота из «Не подходит» можно добавить в сравнение вручную (п. 3.4.4): экран показывает список
проваленных критичных проверок и просит подтверждения, робот получает метку «Добавлен вручную».

## 4. Балл и факторы

У исключённых роботов балла нет (`score = null`). Для остальных балл 0–100 — сумма вкладов
пяти факторов; вклад = вес × значение фактора (округление до 0,1).

| Фактор | Вес | Значение (0–100) |
|---|---|---|
| Экономика (окупаемость) | 0,35 | `100 − 15 × окупаемость_лет` при покупке расчётного числа роботов; не окупается — 0; нет производительности — 40 |
| Производительность | 0,25 | `perfOpsPerHour / наибольшая_производительность_среди_кандидатов × 100` (системы `asrs` в максимуме не участвуют); нет данных — 0 |
| Соответствие объекту | 0,20 | доля пройденных проверок × 100 |
| Полнота и достоверность данных | 0,10 | 100 — данные подтверждены, 40 — нет |
| Доступность поставки | 0,10 | 100 — «В наличии», 75 — указан другой срок поставки, 30 — не указано |

Экран «Подбор» показывает каждый фактор с весом и вкладом («Из чего сложился балл»).

## 5. Недостающие данные

Для каждого кандидата перечисляются пустые характеристики из списка: грузоподъёмность,
производительность, минимальная ширина прохода, время автономной работы, время зарядки,
срок службы. Список показывается строкой «Нет данных: …» и в печатном отчёте.

## Пример: демо-склад

Параметры: масса единицы 350 кг, проходы 3 м, потребность 447 опер./ч, смена 8 ч; процессы — все пять.

| Робот | Статус | Балл | Почему |
|---|---|---|---|
| Логимов AMR-600 | Рекомендовано | 74,4 | все проверки пройдены, лучшая окупаемость |
| Автопогрузчик ФМР-16 | Не подходит | — | нужен проход 3,2 м, на объекте 3 м |
| Шаттл-система АСХ-Шаттл | Не подходит | — | грузоподъёмность 50 кг меньше 350 кг |
| Тягач АТ-1000 Лайт | Требует проверки | 39,6 | нет данных о ширине прохода |

## Ограничения

- Правила работают только в модели моков; серверное ядро — заглушка.
- Поля аэропорта и больницы «Зона операции», «Требования безопасности», «Закрытые и открытые
  зоны», «Санитарная обработка», «Ограничения доступа», а также габариты груза в подборе не
  используются.
- Связи робота с процессом нет: при выборе процессов фильтруются только уборщики.
- Нет проверок точности позиционирования, навигации, условий эксплуатации, связи и интеграции
  (этих характеристик нет в модели робота).
- Веса факторов и предел в 40 роботов — допущения команды, в интерфейсе не настраиваются.
- Фактор «Экономика» считается по сценарию покупки и не учитывает аренду.
