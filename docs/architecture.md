Документ для п. 6.3 и 3.8.3 ТЗ. Описывает то, что есть в репозитории, и отдельно — целевую схему.

## Почему модульный монолит

Бэкенд задуман как один процесс (`Robo.Api`) с отдельной библиотекой расчёта (`Robo.Core`):

- **Одна точка развёртывания.** Для экспресс-оценки с пилотной нагрузкой до 50 пользователей
  (п. 4.3.1) отдельные сервисы не нужны, а контейнеров и сетевых вызовов меньше.
- **Расчёт изолирован.** `Robo.Core` не зависит ни от ASP.NET, ни от EF: в `Robo.Core.csproj`
  нет ни одного пакета. `Calculate(request, robots, config)` — функция без побочных эффектов:
  её можно тестировать без БД (`backend/tests`) и при необходимости вынести в отдельный сервис.
- **Расширение данными, а не кодом** (п. 4.2.6): типы объектов, поля форм, процессы и нормативы
  лежат в `backend/config/*.json`; формы фронтенда строятся по описанию полей (`DynamicForm`).
- **Единый контракт** между фронтендом, мок-сервером и API — раздел 5 CLAUDE.md и
  `frontend/src/types/api.ts`; C#-зеркало — `Robo.Core/Contracts`.

## Схема данных

Сущности контракта (`frontend/src/types/api.ts`):

```
User (id, email, name, role: user|admin)
  └─< Project (id, name, objectType, params, assumptions, createdAt, updatedAt)
        └─< CalculationRecord (id, createdAt, request: CalcRequest, result: CalcResult)

ObjectType (code, fields[], groups[], processes[], demoParams, layout)   — справочник, JSON
Robot (id, характеристики, цены, источник)                              — каталог
```

- `CalcResult` содержит подбор, три сценария с показателями и формулами, чувствительность,
  допущения, версии модели и данных. Запись расчёта хранит запрос и результат целиком — так
  расчёт воспроизводится (п. 3.1.5).
- Параметры объекта (`params`) — словарь «ключ поля → значение»: набор полей задаёт тип объекта.

Сейчас эти данные живут в мок-сервере и `localStorage`. **Таблиц в БД нет** — `DbContext` и
миграции не созданы. Целевая схема: таблицы `users`, `robots`, `projects`, `calculations`
(`request` и `result` — JSON), справочники — из `backend/config`.

## Контракт API

REST, JSON, префикс `/api/v1`, ключи camelCase, id — строки (UUID), даты — ISO 8601 UTC,
деньги — рубли с НДС. Ошибки — формат ProblemDetails с полем `code`. Полный контракт —
раздел 5 CLAUDE.md, примеры запросов и ответов — `docs/api-examples.md`, статус эндпоинтов —
`docs/api.md`. Как API вызывает ядро — `docs/core-api.md`.

## Возможные интеграции (п. 3.8.3)

Интеграции **не реализованы**; ниже — как их подключить к существующему контракту.

| Система | Что берём / отдаём | Куда в платформе |
|---|---|---|
| **WMS** (управление складом) | Суточные объёмы входящих, внутренних и исходящих операций, число SKU, пиковая нагрузка по часам, длины маршрутов | Параметры объекта проекта (`params`: `inboundPerDay`, `internalPerDay`, `outboundPerDay`, `skuCount`, `processPerfPerHour`, `avgRouteM`). Сейчас тот же путь — CSV по шаблону на шаге «Параметры»; интеграция — эндпоинт импорта параметров проекта |
| **ERP / 1С** | Численность и стоимость персонала, тарифы, фактические цены закупки оборудования; обратно — расчёт для бюджета | `staffCount`, `staffCostMonthRub`, цены в каталоге; выгрузка результата расчёта (CSV сейчас, Excel — план) |
| **Системы мониторинга оборудования** | Фактическая производительность, простои, время зарядки работающих роботов | Характеристики робота в каталоге (`perfOpsPerHour`, `autonomyH`, `chargeTimeH`) с источником и датой; сравнение с KPI симуляции |
| **Аналитические продукты ФЦ БАС** | Каталог решений и цены (`catalog_export_v5`), обезличенные расчёты | Импорт каталога в админке; выгрузка `CalculationRecord` |

Общий способ: адаптер на стороне `Robo.Api` преобразует данные внешней системы в сущности
контракта (`Params`, `RobotInput`) и вызывает те же операции, что и интерфейс. Ядро расчёта при
этом не меняется. Для импорта нужны эндпоинты из п. 3.8.2 ТЗ — сейчас их нет.

## Ограничения

- Бэкенд — каркас: из контракта есть только `/robots` (без хранения). Демо работает на мок-сервере.
- БД, авторизации, серверной изоляции проектов нет; схема данных описана как целевая.
- Расчёт на сервере — заглушка; рабочая модель — в мок-сервере фронтенда.
- Интеграции с WMS, ERP, 1С, мониторингом только описаны.
- OpenAPI-спецификация не сгенерирована (пакет подключён, в `Program.cs` не включён).
